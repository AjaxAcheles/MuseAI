## Background you need

The loop is: `draft_prose` → `audit` (programmatic, model-free) → `critics`
(the single continuity critic) → `mode_selector` → `commit` | `revise` |
`review`.

- `museai/fsm/nodes/audit.py` writes programmatic `FailureObject`s into
  `state["critic_failures"]` with `critic_source == "programmatic_audit"`.
- `museai/fsm/nodes/critics.py` appends the model critic's failures to the same
  list (the reducer `accumulate_or_reset` in `museai/fsm/state.py` accumulates,
  and resets on an explicit `[]`). It then computes:
  ```python
  total = len(state["critic_failures"]) + len(failures)
  best_count = state["best_seen_failure_count"]
  improved = best_count is None or total < best_count
  pre_revise = state["pre_revise_failure_count"]
  progressed = pre_revise is None or total < pre_revise
  ```
  and stores `best_seen_draft` / `best_seen_failure_count` as a running minimum,
  plus `last_cycle_improved = progressed`.
- `museai/fsm/nodes/revise.py` reads `state["current_draft_text"]` and
  `state["critic_failures"]`, rewrites, and returns the new text plus
  `"pre_revise_failure_count": len(failures)` and `"critic_failures": []`.
- `museai/fsm/routers/mode_selector.py` routes on those.

## Fix 1 — a revision that makes the draft worse compounds into the next cycle

### The bug

Revision is not monotonic. Observed in a real six-beat run:

- `c02-b02`: **6 failures in, 7 out** (`phrase_echoes` went 1 → 3, and the
  critic switched from `CONTRADICTS_PRIOR_PROSE` to `CONTRADICTS_CHARACTER`).
- `c02-b03`: **5 in, 10 out**.

Both beats parked. When a rewrite regresses, `revise` still returns the worse
text as `current_draft_text`, so the **next** revision cycle starts from the
worse draft and can degrade further from there.

`best_seen_draft` protects the *output* — it is a running minimum, so the
salvage path can always recover the best text seen. But it does not protect the
*loop*: the cycles in between are spent digging downward from a draft already
known to be worse than one the system is holding.

This got sharper recently. `mode_selector`'s `no_progress` rule used to stop
the loop after one non-improving cycle, but it was deliberately amended so that
**audit-only** failures (deterministic density measurements) are exempt and get
to spend the full `revision_retry_cap`:

```python
no_progress = (
    retry_count > 0
    and not state["last_cycle_improved"]
    and not audit_only
)
```

That was the right call for its own reasons, but it means a beat whose
outstanding failures are all programmatic now gets up to `revision_retry_cap`
consecutive full rewrites, each one starting from whatever the previous rewrite
produced — including a worse one. The brake that used to catch compounding is
gone for exactly the case that now rewrites most often.

### The fix

Make each revision cycle start from the best draft seen, not from the last one
produced.

1. **Add `best_seen_failures` to `OrchestratorState`** in `museai/fsm/state.py`,
   alongside `best_seen_draft` / `best_seen_failure_count`:
   ```python
   best_seen_failures: list[FailureObject] | None
   ```
   It is the failure list that went with `best_seen_draft`. Initialise it to
   `None` in `make_initial_state`, and reset it wherever `best_seen_draft` is
   reset — check `museai/fsm/nodes/commit.py` around line 413, which resets the
   per-beat scoring fields, and keep it consistent with them.

   **This field must be a plain state key, not an accumulating reducer.** Do not
   annotate it with `accumulate_or_reset`.

   Give it the same style of explanatory comment the neighbouring fields have.

2. **In `museai/fsm/nodes/critics.py`**, when `improved` is true, record the
   combined failure list alongside the draft:
   ```python
   "best_seen_failures": combined if improved else state["best_seen_failures"],
   ```
   where `combined` is the full outstanding set for this draft — the audit
   failures already in `state["critic_failures"]` plus the critic's `failures`
   from this pass. That is the same set `total` counts, so the stored list and
   the stored count always agree. Build it explicitly; do not recompute it
   differently from `total`.

3. **In `museai/fsm/nodes/revise.py`**, at the top of `revise_prose`, before
   anything else uses the draft: if the draft it was handed is known to be worse
   than the best seen, roll back to the best seen and revise *that* instead.

   The condition is all of:
   - `state["best_seen_draft"]` is not `None`
   - `state["best_seen_failures"]` is not `None`
   - `state["best_seen_failure_count"]` is not `None`
   - `state["best_seen_failure_count"] < len(failures)` — strictly worse, so an
     equal-count rewrite is left alone (it may have traded one problem for a
     different one of the same count, and thrashing back and forth would be
     worse than continuing)
   - `state["best_seen_draft"] != draft` — nothing to do when they are the same
     text

   When it holds, set `draft` and `failures` from the best-seen pair, and log it
   with `log_node_event("revise", event="rolled_back", beat_id=..., ...)`
   carrying the failure counts before and after the rollback so the decision is
   visible in the run log.

   Both `draft` and `failures` must be replaced **together**. Replacing the text
   without the failure list would hand the reviser findings that describe prose
   that is no longer there, and `locate()` would then fail to find the spans and
   silently force a full rewrite. This pairing is the whole point of storing
   `best_seen_failures`.

   Everything downstream — `locate`, `span_mode`, the `whole_draft` check, the
   splice loop, the returned `pre_revise_failure_count: len(failures)` — must
   then operate on the rolled-back values. Make sure `pre_revise_failure_count`
   reflects the list actually being revised, because `critics.py` scores the
   next cycle against it.

   Note the existing guard at the top of the function that raises
   `DraftingError` when `failures` is empty. That must still run, and the
   rollback must not be able to produce an empty list (it cannot: the condition
   requires `best_seen_failure_count < len(failures)`, and the stored count
   matches the stored list — but do not write code that depends on that
   silently, keep the guard where it is).

4. `mode_selector.py` needs no change. Leave it alone.

or `tests/test_critic_resilience.py`, `tests/test_mode_selector.py`) and add to

  equals the stored count.
- The rolled-back `pre_revise_failure_count` equals the best-seen count, so the
  next critics pass scores against the right baseline.

## Fix 2 — the beat planner under-decomposes chapters

### The bug

In the observed run the four chapters received **1, 3, 1, 1** beats. Three of
four chapters were a single beat, and the entire four-chapter arc came to 2,591
words. Nothing in the system constrains this: `generation.word_count_target` is
a whole-manuscript stop signal read by `commit_router` and the dashboard, and is
never shown to the beat planner. The planner prompt asks for "an ordered
sequence of beats" and gives no floor, so on a small local model it routinely
returns one.

A single-beat chapter is not a decomposition. It also silently disables the
emotional-arc check, which skips any chapter shorter than
`generation.intensity_min_beats`.

### The fix

Add a bounded semantic re-prompt for under-decomposition, modelled **exactly**
on the existing intensity re-prompt in `museai/fsm/nodes/plan_beat.py` (see
`_INTENSITY_CORRECTION`, `_is_flat_hot`, and the
`for _ in range(config.generation.planner_intensity_retries):` loop around line
630). Follow that pattern closely — same structure, same logging shape, same
"re-prompt then accept whatever comes back" bounded discipline.

1. **Two new config keys** in `GenerationConfig` (`museai/core/config.py`),
   placed next to the other planner keys:
   - `min_beats_per_chapter: int = 3` — the fewest beats a chapter plan may
     contain before the planner is asked to decompose further.
   - `planner_decomposition_retries: int = 1` — how many times to re-prompt.

   `min_beats_per_chapter` must be validated `>= 1` (add it to the existing
   `_positive` validator list that already covers `intensity_min_beats` etc.).
   `planner_decomposition_retries` must be validated `>= 0` — find how
   `planner_intensity_retries` is validated and treat the new key identically.

   Add both to `config.yaml` and `config.example.yaml` with an explanatory
   comment in the file's established voice, citing the observed 1/3/1/1
   decomposition as the reason.

2. **A `_DECOMPOSITION_CORRECTION` message**, alongside `_INTENSITY_CORRECTION`.
   It must ask the planner to break the chapter into more beats — each with its
   own required_change and observable_event — while keeping the chapter's
   obligations fully covered and still assigned to at least one beat. Say
   plainly that a chapter delivered as a single beat is not a decomposition. Do
   not name a specific number in the constant itself; format the configured
   minimum into it so the message and the config cannot drift apart.

3. **The retry loop**: after the JSON array comes back and **before** the
   intensity loop, if `len(planned) < config.generation.min_beats_per_chapter`,
   log a warning event (`event="decomposition_reprompt"`, with `chapter_id` and
   `beats=len(planned)`), publish to the stream bus the way the intensity path
   does, append the assistant's JSON and the correction as a new user turn, and
   re-call `call_llm_for_json_array` with the identical arguments the existing
   calls use (`element_keys=("intent",)`, `item_validator=_validate_beat_item`,
   the same retries/tools/caps). Bound it by
   `config.generation.planner_decomposition_retries`.

   Run decomposition **before** intensity: the intensity check is skipped on
   short chapters, so widening the chapter first is what lets the arc check see
   it at all.

   After the retries are spent, **accept whatever came back**. Do not raise, do
   not park, do not block. A planner that will not decompose still produces a
   usable plan, and the FSM must not stall on it.

4. Tell the beat planner the floor up front as well, so the re-prompt is the
   fallback rather than the primary mechanism. In
   `museai/prompts/beat_planner.xml.j2`, add a sentence to the system block
   stating the minimum number of beats, fed from the config value through the
   existing `render_messages` call in `plan_beat.py` (add the variable to the
   render call; do not hardcode a number in the template).

### Tests for Fix 2

Add to `tests/test_planners.py` (it already has beat-planner coverage; follow
its fixtures and style):
- A plan returning 1 beat with `min_beats_per_chapter: 3` triggers exactly one
  re-prompt, and the second reply's beats are the ones used.
- A plan returning 3 beats triggers **no** re-prompt.
- With `planner_decomposition_retries: 0`, an under-decomposed plan is accepted
  as-is with no extra LLM call.
- After the retries are exhausted and the planner still returns 1 beat, the node
  **succeeds** with that 1 beat — no exception.
- The configured minimum reaches the rendered prompt.
