## Fix 1 — a truncated critic verdict is thrown away even when most of it parsed

### The evidence

From a full run on 2026-08-20 (11 beats, `reasoning_effort: none` on every role):

- `critic reply was cut off (finish_reason='length')` — **5 times**
- `event=empty_reply` — **0 times**

That combination is the whole point. `museai/fsm/nodes/critics.py` treats
truncation as the *reasoning-burn* failure mode, where the model spends its
entire budget deliberating and returns zero characters. With
`reasoning_effort: none` that mode no longer happens — and it demonstrably did
not happen here. What happens instead is mundane: the critic found several
problems, and a verdict carrying multiple findings (each with an `error_code`,
a quoted `offending_text`, and a `suggested_fix`) simply exceeded
`agents.critic.max_output_tokens: 4096`.

So all five of those replies **contained text**. Very likely well-formed JSON
for the first N findings, cut off partway through the last one.

### The bug

In `critics.py` (~line 460), inside the retry loop:

```python
try:
    if last_truncated:
        raise StructuredOutputError(
            "critic reply was cut off (finish_reason='length'): "
            + response_truncation_remedy(response, config.endpoint_for("critic"))
        )
    parsed_failures = parse_failure_objects(response.text)
    ...
```

Truncation raises **before any attempt to parse**. A reply containing seven
complete, valid findings and a half-written eighth is discarded in full. The
node then burns its `critic_parse_retries` budget re-asking, and only if the
whole ladder is exhausted does the degraded path at ~line 558 finally try
`parse_failure_objects(last_text, lenient=True)` — the salvage that would have
worked on the first reply.

Note the irony already in the file: `_TRUNCATION_FINAL_MESSAGE` tells the model
"a partial array is far better than another cut-off reply" — the model is invited
to answer partially, but the parser refuses to read a partial answer.

### The fix

**(a) Try to salvage before giving up.** When `last_truncated` is true *and*
`response.text` has content, attempt a lenient parse of what arrived. If it
yields at least one valid finding, accept those findings and proceed as a
successful (if incomplete) verdict rather than raising.

Requirements:
- Use the existing `parse_failure_objects(..., lenient=True)`. Do not write a
  second parser.
- Run the salvaged findings through the **same** downstream pipeline the normal
  path uses — `_locatable_findings`, `_sanitize_borrowed_fixes`, and
  `_cap_findings_per_code`. A salvaged finding must not skip the guards that a
  normally-parsed one passes through. This matters: those guards are what keep
  an unlocatable or plagiarised `suggested_fix` out of the reviser.
- Log it as its own greppable event — `event=truncated_verdict_salvaged` with
  `beat_id`, `attempt`, and the number of findings recovered — so the rate is
  visible in the run log rather than inferred.
- Set the existing `lenient_used` flag so the health/telemetry path already in
  the file reports it honestly. Check how `lenient_used` feeds
  `log_node_event`/`_health` and keep that consistent.
- **Only when the salvage yields nothing** should it raise as it does today and
  fall through to the retry ladder. An empty reply must behave exactly as it
  does now.

**(b) Stop asserting a cause the code cannot know.**
`_TRUNCATION_RETRY_MESSAGE` currently states:

> "Your previous reply was cut off before it produced any JSON — the whole reply
> went to reasoning, with nothing left for the answer."

That is now false in the common case. Split the two situations:

- **Empty reply** (truncated, no text): keep the existing message — that
  diagnosis is still correct and is backed by the 2026-07-25 postmortem cited in
  the comment above it. Do not weaken it.
- **Truncated with text**: a new message saying the verdict ran past the reply
  budget, and asking for the *most important* findings only, in a shorter reply
  — fewer findings, shorter `suggested_fix` values. Do not invite `[]`; the
  existing comment explains at length why an unreadable verdict must never be
  laundered into a clean pass, and that reasoning applies here unchanged.

Keep `_TRUNCATION_FINAL_MESSAGE`'s escalation behaviour for a repeat truncation.

**(c) Raise the ceiling, as defence in depth.** In `config.yaml` and
`config.example.yaml`, raise the critic's budget:

```yaml
  critic:
    max_output_tokens: 6144
    output_reservation: 6144
```

The invariant the config validator enforces is `max_output_tokens <=
output_reservation`, and `output_reservation < context_window` (20000), so 6144
is legal. Update the existing explanatory comment on those two keys to record
*why* it moved: five legitimate multi-finding verdicts hit the 4096 ceiling in
the 2026-08-20 run, with zero empty replies, so the cap was binding on real
answers rather than on runaway reasoning. Keep the existing note that the two
values must move together.

Do **not** treat (c) as the fix on its own. Raising a ceiling only moves where
the cliff is; (a) is what makes the cliff survivable.

### Tests for Fix 1

Add to `tests/test_critic_resilience.py` (it already covers the parse ladder —

## Fix 2 — the truncation remedy names a config key that does not bind

`museai/llm/structured.py` line ~162 (and the related strings at ~174, ~184,
~187) tell the operator:

> "raise endpoint.max_output_tokens (or leave it unset to omit the cap)"

For four of the five roles that is the wrong key. `config.yaml` sets
`max_output_tokens` under `agents.critic` and `agents.reviser`; those per-agent
overrides are what actually bound the call. An operator who follows this advice
edits `endpoint.max_output_tokens` and observes no change.

`response_truncation_remedy` already resolves the *effective* cap correctly via
`response.effective_max_tokens` — it is only the human-readable string that
points at the wrong place.

### The fix

Thread the agent role through so the message can name the key that actually
bound:

- Give `response_truncation_remedy` an optional `role: str | None = None`
  parameter, and pass it down to `truncation_remedy`.
- When a role is given, the message names `agents.<role>.max_output_tokens`;
  with no role it keeps naming `endpoint.max_output_tokens` exactly as now.
- Update the call sites so each passes the role it is calling for. Find them all
  — `grep -rn "response_truncation_remedy" museai/` — they include the critic
  (`"critic"`), the reviser (`"reviser"`), and the planners. Each of those call
  sites already knows its own role, usually right next to a
  `config.endpoint_for("<role>")` call; use that same literal.
- Where the message mentions `endpoint.context_window` or
  `endpoint.output_reservation`, apply the same treatment only if those are also
  per-agent overridable — check `AgentEndpointOverride` in
  `museai/core/config.py` and be accurate. Do not name a key that cannot be set.

The default (no role) behaviour must be unchanged so existing tests and any
caller without a role still get today's wording.

### Tests for Fix 2

- `response_truncation_remedy(resp, endpoint, role="critic")` names
  `agents.critic.max_output_tokens` and does **not** name
  `endpoint.max_output_tokens`.
- With no role, the message is byte-identical to today's.
- The critic's truncation error, raised end-to-end, names the critic's key —
  assert on the message the node actually produces, not just the helper.

## Fix 3 — a rejected span rewrite is thrown away and the whole beat regenerated

In the 2026-08-20 run, `event=span_rejected` fired **7 times**, and all seven
were the same reason:

```
reason="replacement repeats surrounding prose: 'through the black rectangle of the open gate'"
reason="replacement repeats surrounding prose: 'steady and unhurried as the steam curled from'"
...
```

`replacement_rejection` in `museai/fsm/nodes/revise.py` is working exactly as
designed — it is stopping duplicated paragraphs from being spliced into the
manuscript, which is the bug it was written for. The waste is what happens next:
the LLM call that produced the rejected replacement is discarded, `span_mode` is
set to `False`, and the entire beat is regenerated from scratch. Seven paid
calls thrown away in one run, plus a full rewrite each time — and a full rewrite
of prose the critic only faulted in one span is exactly the drift the span path
exists to avoid.

### The fix

Give the span rewrite one bounded second chance that tells the model why its
first attempt was refused, before falling back to the full rewrite.

- Add `span_rejection_retries: int = 1` to the **`revision:`** section of the
  config model (`RevisionConfig` in `museai/core/config.py`), validated `>= 0`,
  and add it to `config.yaml` and `config.example.yaml` with a comment recording
  the 7/7 observation above. This section already holds the other span-splice
  bounds (`fuzzy_growth`, `echo_min_words`, …) so it is the right home.
- In the span loop in `revise_prose`: when `replacement_rejection` returns a
  reason, re-prompt that span up to `span_rejection_retries` times, appending
  the rejection reason to the messages as a correction turn — state plainly that
  the replacement repeated prose from the surrounding beat (quote the echoed run
  the guard found), and that the rewrite must not reuse the surrounding wording.
  Follow the bounded-retry idiom already used by `_INTENSITY_CORRECTION` and
  `_DECOMPOSITION_CORRECTION` in `plan_beat.py`: a module-level message constant,
  a `for _ in range(...)` loop, then accept or fall through.
- If a retry produces an acceptable replacement, splice it and carry on in span
  mode. If the retries are spent and it is still rejected, fall back to the full
  rewrite **exactly as today** — do not change that fallback, and do not splice a
  replacement the guard rejected.
- Keep logging `event=span_rejected` for each rejection so the rate stays
  visible, and add the attempt number to it.
- `span_rejection_retries: 0` must reproduce today's behaviour exactly.

### Tests for Fix 3

Add to `tests/test_revise.py`:
- A first replacement that echoes surrounding prose, a second that does not →
  span mode is kept, the good replacement is spliced, and no full rewrite runs.
- Both attempts echo → falls back to full mode, exactly as today.
- `span_rejection_retries: 0` → a single rejection goes straight to full mode,
  with no second span call.
- The correction message sent on the retry contains the echoed phrase the guard
  reported.
