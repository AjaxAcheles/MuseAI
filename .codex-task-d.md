## The bug, observed live

A real run on 2026-08-20 parked on the **first beat of the first chapter**,
with three of its four revision retries unspent. The log:

```
critics  event=critiqued  critic_failures=1 error_codes=['CONTRADICTS_CHARACTER']
                          total_failures=1 best_seen_failure_count=1
                          pre_revise_failure_count=None progressed=True
mode_selector route destination=revise failures=1 retry_count=0

revise   event=revised    mode=span failures_fixed=1 spans_located=1
                          whole_draft_failures=0 retry_count=1 words=458

audit    event=audited    ... failures=0
critics  event=critiqued  critic_failures=1 error_codes=['CONTRADICTS_THREAD']
                          total_failures=1 pre_revise_failure_count=1
                          progressed=False
mode_selector route destination=review failures=1 retry_count=1
                          revision_retry_cap=4 last_cycle_improved=False
                          audit_only=False no_progress=True

review   event=review_needed
manager  event=run_parked_for_review
```

The reviser was handed one finding, `CONTRADICTS_CHARACTER`. It located the
span, rewrote it, and **that finding is gone**. The critic then raised a
completely different finding, `CONTRADICTS_THREAD`, against the new prose.

The count went 1 → 1, so `critics.py` computed `progressed = total < pre_revise`
= `False`, and `mode_selector`'s `no_progress` rule sent the beat to human
review. The revision did its job and was scored as a stall.

This is the other half of report §4.4, which recorded the same signature — "the
critic switched from `CONTRADICTS_PRIOR_PROSE` to `CONTRADICTS_CHARACTER`" — and
attributed it only to the failure count rising. Equal counts have the same
problem and are worse, because they look like a stall rather than a regression.

### Why it matters

`no_progress` exists to stop a beat burning a full critic pass re-running an
identical, non-improving cycle — the observed case was a draft stuck at an
unchanged `passive_density` across four retries. That is a real thing to stop.

But its test is *arithmetic on a count*, and a count cannot distinguish:

- **a genuine stall** — the same finding comes back, the rewrite changed nothing
  that mattered; and
- **normal iteration** — the finding it was asked to fix is gone, and the critic
  found something else in the new prose.

The second is what a revise → critique loop is *supposed* to look like on a
first pass, and `revision_retry_cap` (4) already bounds how long it may go on.
Parking at retry 1 of 4 throws away three quarters of the configured budget and
puts a beat in front of a human that the machine had not finished working on.

## The fix

Progress should mean **"the findings the reviser was handed are gone"**, not
merely "there are fewer findings than before".

### 1. Record what the reviser was asked to fix

In `museai/fsm/state.py`, add a field next to `pre_revise_failure_count`:

```python
pre_revise_failure_signatures: list[str] | None
```

It is the identity of each failure handed to the last `revise`. Give it the
same style of explanatory comment its neighbours have — say that it exists
because a count alone cannot tell a stall from ordinary iteration, and cite the
2026-08-20 first-beat park.

Initialise to `None` in `make_initial_state`, and reset it wherever the other
per-beat scoring fields are reset — see `museai/fsm/nodes/commit.py` (it already
resets `pre_revise_failure_count`, `best_seen_draft`, `best_seen_failures`,
`last_cycle_improved`); keep it consistent with those.

It is a plain state key. Do **not** annotate it with the `accumulate_or_reset`
reducer.

### 2. A failure's signature

Add a small module-level helper — put it in `museai/fsm/state.py` next to
`FailureObject`, since both `revise.py` and `critics.py` need it and neither
should import the other:

```python
def failure_signature(failure: FailureObject) -> str:
```

It must identify *the same problem in the same place*, and must be stable across
a rewrite that did not touch the problem. Build it from the failure's
`error_code` and a whitespace-normalised, casefolded form of its
`offending_text`. Normalise whitespace by splitting and rejoining on single
spaces, so a reflowed line is still recognised as the same finding.

Note that a density failure's `offending_text` is only its first offending
sentence — that is fine here: if the density breach persists, the first
offending sentence is very likely the same one, and if the prose changed enough
to move it, the finding genuinely is a different one.

### 3. `revise.py` writes the signatures it acted on

In `museai/fsm/nodes/revise.py`, `revise_prose` already returns
`"pre_revise_failure_count": len(failures)`. Add alongside it:

```python
"pre_revise_failure_signatures": [failure_signature(f) for f in failures],
```

Critically, this must use the **same `failures` list the reviser actually
worked from** — i.e. after the best-seen rollback that already exists at the top
of that function may have replaced it. The count and the signatures must always
describe the same list, or the next cycle scores against a baseline that never
existed.

### 4. `critics.py` scores identity, not just count

In `museai/fsm/nodes/critics.py`, the current logic is:

```python
pre_revise = state["pre_revise_failure_count"]
progressed = pre_revise is None or total < pre_revise
```

Change it so a cycle counts as progress when **either**:

- the total dropped (`total < pre_revise`) — unchanged, still progress; **or**
- none of the failures the reviser was handed are still present. Compare the
  signatures of the current combined failure set (the `combined` list already
  computed there — audit failures plus this pass's critic failures) against
  `state["pre_revise_failure_signatures"]`. If the intersection is empty, every
  finding the reviser was asked to fix is gone, and this is progress.

`pre_revise is None` (no revise has run yet) must still short-circuit to
`True`, exactly as now. A `pre_revise_failure_signatures` of `None` or `[]` must
not crash and must not be treated as "all findings cleared" on its own — guard
it explicitly.

Add `progressed_by_signature` (or similarly named) to the existing
`log_node_event("critics", event="critiqued", ...)` call so the run log shows
*which* of the two rules granted progress. This is the field that will explain a
future park, so it must be visible.

### 5. `mode_selector.py`

No logic change. But its module docstring and the long comment above the
`no_progress` computation both describe the old count-only rule, and they will
be wrong once this lands. Update them to state the rule accurately: a beat is
parked for no progress only when the findings it was told to fix are still
there. Keep the existing explanation of *why* the rule exists at all.

### 6. Do not add a config key

The retry ceiling is already `generation.revision_retry_cap`. An
A→B→A→B alternation between two findings is bounded by it, which is exactly
what it is for. Do not add a new threshold for this.

## Tests

Add to `tests/test_critics.py` and `tests/test_mode_selector.py` (follow their

Cover:
1. **The observed case.** Pre-revise held one `CONTRADICTS_CHARACTER`; the new

   finding (not progress).
4. **A partial fix.** Two findings in, one of them still present, count
   unchanged at 2 (one fixed, one new) → intersection is non-empty → not
   progress by signature. Confirm the count rule still governs when the total
   drops.
5. **Count drop still wins.** 3 findings in, 2 out, all three signatures still
   present → progress, because the total fell.
6. **`pre_revise_failure_signatures is None`** (first cycle) → progress, no
   crash.
7. **`revise` writes signatures matching the list it revised**, including after
   a best-seen rollback — assert the signatures correspond to the rolled-back
   failures, not the ones originally in state.
