## Fix 1 — `fuzzy_find` stalls the entire web server (the important one)

### The measurement

`museai/fsm/nodes/revise.py::fuzzy_find` slides a `difflib.SequenceMatcher`
across every word boundary of the draft, once per failure. It is pure
synchronous CPU, called from `async def revise_prose` via `locate`, so it runs
**on the asyncio event loop**. While it runs, the Quart server serves nothing.

Measured on this project's own longest committed beat (1,766 words / 10,451
chars, 1,766 candidate window starts):

| failures | blocking time |
|---|---|
| 1 | 0.43 s |
| 4 | 1.75 s |
| 8 | 3.99 s |

With `generation.revision_retry_cap: 4` that is up to ~16 s per beat during
which `/status` does not answer. This is not hypothetical: during a live run on
2026-08-20 a polling client using a 10 s timeout got empty replies repeatedly
and a 15 s timeout also failed; only a 90 s timeout was reliable. The LLM client
is *not* the cause — it correctly uses `httpx.AsyncClient` with `async with`, so
network I/O already yields. This is CPU.

### The fix — two independent parts, do both

**(a) Move the work off the loop.**

In `revise_prose`, the span-location step is currently:

```python
located = [(failure, locate(draft, failure.offending_text)) for failure in failures]
```

Move that whole comprehension into a worker thread with
`asyncio.to_thread`, e.g. a module-level sync helper
`def _locate_all(draft, failures) -> list[tuple[FailureObject, tuple[int,int] | None]]`
awaited as `located = await asyncio.to_thread(_locate_all, draft, failures)`.

Keep `locate` and `fuzzy_find` **synchronous** — they are pure functions, they
are used directly by tests, and making them async would churn every caller.
Only `revise_prose` changes how it calls them.

`fuzzy_find` reads defaults from `get_node_config()`. That is a plain module
global in `museai/fsm/nodes/deps.py` (not a contextvar), so reading it from a
worker thread is safe. Do not add locking.

**(b) Make it cheaper.**

The loop already skips windows using `matcher.quick_ratio()` as a cheap upper
bound. `SequenceMatcher` also offers `real_quick_ratio()`, which is a *looser
and even cheaper* upper bound (it only compares sequence lengths). Add it as a
pre-prefilter before `quick_ratio()`:

```python
if matcher.real_quick_ratio() < best_ratio:
    continue
if matcher.quick_ratio() < best_ratio:
    continue
```

This is **behaviour-preserving**: both are documented upper bounds on `ratio()`,
so any window they reject could never have exceeded `best_ratio` anyway. The
selected span for any input must be identical before and after.

Do not change `fuzzy_find`'s signature, its threshold semantics, or the
`min_span_chars` early-`break`.

## Fix 2 — synchronous SQLite inside async nodes

`sqlite3` is a blocking driver. These `async def` functions call `connect_db`
and run queries directly on the event loop:

- `museai/fsm/nodes/commit.py` (~line 274, in `async def commit_transaction`)
- `museai/fsm/nodes/assemble_context.py` (~line 225)
- `museai/fsm/nodes/plan_beat.py` (~line 517)
- `museai/fsm/nodes/plan_chapter.py` (~line 154)

Also check `museai/fsm/routers/commit_router.py` (~line 119) and
`museai/fsm/export.py` — but see the caveat below before touching them.

Individually these are milliseconds, not seconds; this is a jitter and
correctness-of-layering problem, not the cause of the multi-second stalls in
Fix 1. Fix it anyway, carefully, and do not let it change behaviour.

### How to do it safely

For each `async def` node above, extract the database work into a
**module-level synchronous helper** that opens the connection, does all its
queries and writes, and closes the connection — the entire lifecycle inside one
function — then await it once:

```python
result = await asyncio.to_thread(_read_whatever, config, args...)
```

Hard requirements:

1. **A connection must never cross a thread boundary.** `sqlite3` connections
   are thread-affine (`check_same_thread` defaults to True). Create and close
   inside the same helper, in the same thread. Never return an open connection
   or a live cursor from the helper — return plain data (dicts/lists/values).
   `sqlite3.Row` objects are safe to read after the connection closes, but
   convert to plain dicts if you are at all unsure.
2. **Do not change transaction boundaries.** Where the code uses `with conn:`,
   that whole block stays inside the one helper so the transaction still
   commits or rolls back exactly as it does now. Do not split one transaction
   across two `to_thread` calls.
3. **Do not change SQL, ordering, or error handling.** The upsert-by-id
   idempotency AGENTS.md requires must be preserved exactly.
4. **`commit_router.mode_selector`-style routers**: `museai/fsm/routers/commit_router.py`
   is a LangGraph **conditional edge**, which must stay *synchronous and pure* —
   LangGraph calls it without awaiting. **Do not** make it async and do not add
   `to_thread` there. Leave it alone and say so in your final message.
5. **`museai/fsm/export.py`** is called from `manager.py`. Check whether its
   caller is async. If `export_manuscript` is invoked from an `async` function,
   wrap the *call site* in `asyncio.to_thread` rather than restructuring
   `export.py` itself — it is a sync module with a sync public API used by tests
   and web routes, and changing that signature would ripple.

If any of these turns out to be riskier than it looks once you read it, **skip
that one and say which and why in your final message**. A partial, correct fix
is better than a broken transaction.
